Task 1 · Serial code
ERWYNA1 min
Heading
Task 1 · Serial code
Left side, the main idea
The obvious way to check if k is prime is to try dividing it by everything from 2 up to k minus 1. That is really slow for big numbers. If k is not prime then k = m x p. Those two cannot both be bigger than the square root of k, because then multiplying them would overshoot k. So if there is a factor at all, one of them has to be at or below the square root. That means we can stop at the square root instead of going all the way to k minus 1. We also handle 2 separately so the loop can skip every even divisor and step by 2.
Code snippet to show
limit = (long)sqrt((double)k); for(d = 3; d <= limit; d += 2) { if(k % d == 0) return 0; } return 1;
Right side, how we store the answers
We keep one byte per number in an array and flag the primes as we find them. Reading that array back from the front gives us the primes in ascending order automatically, so we never have to sort anything. That turns out to matter a lot in Task 2 and Task 3. Small n prints to the terminal, large n goes to a text file, as the spec asks.
Small note
We stop the timer before writing the file. Writing 664,579 lines to disk is not part of the calculation we are trying to speed up, and no amount of threads makes the disk faster.
What to say
ERWYNA: For the serial version the main thing is the prime test itself. Instead of dividing by everything up to k minus one, we only go up to the square root of k. The reason is that if k is not prime it factorises into m times p, and those two cannot both be above the square root, because multiplying them would give something bigger than k. So if a factor exists, one of them is at or below the square root, and if we get that far with nothing, k is prime. We also deal with 2 on its own so the loop only tries odd divisors. For storing results we use a flag array, one byte per number. We just mark the primes as we find them, and reading it back from the front gives us ascending order without sorting. That sounds like a small thing but it is what lets the parallel versions avoid locking later. One deliberate choice: the timer stops before the file write, because writing out the list is disk work, not calculation, and threads cannot speed that up.

Task 2 · How we split the work
TAABISH~1 min 15
Heading
Task 2 · How we split the work between threads
Attempt 1
Attempt 1: one block each We copied the approach from the vector cell product example in the Week 3 lab prep. Work out the start point and end point for each thread, and give each one a solid block of numbers. Thread 0 gets 2 to 5 million, thread 1 gets 5 to 10 million, and so on.
Why it was not great
It worked, but it only got us 1.58x on 2 cores when we were hoping for close to 2x. The reason is that our work is not the same size for every number. IsPrime checks divisors up to the square root of k, so checking 9 million takes far more divisions than checking 100. The thread holding the big half is still going long after the other one has finished, and the program has to wait for it at the join.
Attempt 2, what we shipped
Attempt 2: small chunks, taken in turn Instead of one big block each, we hand out blocks of 1000 numbers in rotation. Thread 0 takes the first chunk, thread 1 the next, then it wraps back around. Every thread ends up with a mix of small and big numbers, so they all finish at about the same time. This got us to 1.95x on the same machine.
Box: no locks needed
We did not need a mutex anywhere. Each thread only ever writes to the positions it was handed, so no two threads touch the same element of the array. No shared counter, no critical section, no race condition. The list also comes out sorted on its own, so there is nothing to merge at the end.

What to say
TAABISH: The interesting part of Task 2 was deciding how to split the numbers up. We started with the approach from the vector cell product example in the lab prep, where you work out a start point and end point and give each thread one block. That worked, but we only got 1.58x on two cores and we expected closer to 2. Once we thought about it, the reason is that the work is not the same size for every number. So we changed it to hand out chunks of a thousand numbers in rotation instead. Each thread gets a mix of small and big numbers, they finish at about the same time, and that took us from 1.58 to 1.95. Each thread only writes to the slots it was given, so no two threads ever touch the same element, which means no race condition and nothing to lock.

Task 3 · OpenMP
TAABISH~1 min
Heading
Task 3 · OpenMP
The whole parallel bit
#pragma omp parallel for schedule(dynamic, 1000) for(k = 2; k < n; k++) { if(IsPrime(k)) pFlags[k] = 1; }
Point to make
That one pragma replaces about forty lines of thread creating, argument passing and joining from Task 2. We did not have to work out start points and end points at all, OpenMP does the splitting. The schedule clause is doing the same job as our chunks in Task 2. With static, the split is decided before the loop starts, so the thread with the big numbers finishes last again. With dynamic, a thread comes back for another chunk as soon as it finishes one.
Being honest about the schedules
We timed static, dynamic and guided. On our machine they all landed within about 5 percent of each other, which is close enough that we cannot claim one really won. We kept dynamic because the reasoning still holds and the gap should open up on a machine with more cores.
Warning box
Watch out: if you forget the -fopenmp flag it still compiles and still runs, it just quietly ignores the pragma and uses one thread. We got a speedup of exactly 1.00 and spent a while confused before we spotted it.

Conclusion and recommendations
ERWYNA1 min
Heading
Conclusion and recommendations
Column 1, what went well
What went well Both parallel versions got close to the core count, 1.92x and 1.95x on 2 cores. Splitting the numbers into chunks instead of blocks took us from 1.58x to 1.95x. Using a flag array meant no mutex anywhere and no sorting at the end.
Column 2, limitations
Limitations We never hit exactly the core count. Allocating the array, starting the threads and writing the file are all serial, and no number of threads speeds those up. Adding threads past the core count gains nothing. We only had 2 cores to test on, so we cannot say for sure the trend holds at 8 or 16.
Column 3, future work
Future work Use a Sieve of Eratosthenes instead of trial division. It does far less work overall, though splitting it between threads is harder. Test on a machine with more cores to see whether the schedules start to separate. Try timing the file writing separately to see how much of the total it really is.
Recommendation line
Our recommendation: for a loop like this one, use OpenMP. Same speed, far less code, and you get the serial version back just by leaving the flag off. We would reach for POSIX Threads when the work is not a simple loop, or when we need control over what each individual thread is doing.
What to say
ERWYNA: To wrap up. Both parallel versions got close to the core count, 1.92 and 1.95 on two cores. The biggest single improvement we made was changing how the numbers were split, from one block each to chunks taken in turn, which moved us from 1.58 to 1.95. And using the flag array meant we never needed a mutex and never needed to sort. On limitations, we never quite hit the core count exactly, and that is because parts of the program cannot be parallel at all. Allocating the array, starting the threads and writing the file are all serial, so no matter how many threads we add those stay the same. Adding threads past the core count gains nothing. And we only had two cores to test on, so we are careful about claiming the trend continues at eight or sixteen. If we carried on, the obvious next step is a Sieve of Eratosthenes instead of trial division, because it does far less work overall, though it is harder to split between threads. Our recommendation for a loop like this is OpenMP. Same speed, much less code, and you can get the serial version back just by dropping the flag. POSIX Threads makes more sense when the work is not a simple loop.

Likely questions and answers, rehearse these
Is the speedup exactly the number of threads you used? Why not? (this one is almost certain, the spec names it) No. Two reasons. First, parts of the program cannot be split up at all, allocating the array, creating the threads and writing the file are all serial, so they take the same time no matter how many threads we use, and that puts a ceiling on the speedup. Second, the threads do not all finish at exactly the same moment, and creating and joining them costs time that is not doing any actual work. Would you recommend OpenMP over POSIX Threads? (the other one the spec names) For this problem yes. We got the same speed from one pragma that took us about forty lines of thread code to get in Task 2, and if we leave the flag off we get the serial version back for free. We would use POSIX Threads if the work was not a simple loop, for example if different threads had to do completely different jobs, or if we needed to control individual threads. How did you split the work, and is it a good approach? We hand out chunks of a thousand numbers in rotation rather than one block each. It suits this problem because the cost per number rises steadily with the number, so rotating chunks gives everyone a fair mix. It would be less suitable if the expensive parts were scattered randomly, in which case letting threads grab work on demand would adapt better. Where is your critical section? There is not one, on purpose. Each thread only writes to the array positions it was given, so no two threads ever touch the same element. Adding a mutex would just slow it down without making it any more correct. What happens if you use more threads than cores? The speedup stops improving. Once every core has a thread there is nothing left to give the extra ones, so they just take turns on the same cores. Graph 4 shows it going flat after the core count. Why do you stop the timer before writing the file? Because writing the list to disk is not the part we are trying to speed up, and threads cannot make the disk faster. If we included it, it would hide how much the parallel part actually improved. Why only check divisors up to the square root? If k is not prime then k is m times p, and those two cannot both be bigger than the square root, because multiplying them would overshoot k. So if there is a factor, one of them is at or below the square root, and if we find nothing by then, k is prime. Why chunk size 1000? We tried a few sizes and 1000 was comfortably in the range where it stopped making a difference. Too small and the threads spend time swapping between chunks, too big and you drift back towards the one block problem.
